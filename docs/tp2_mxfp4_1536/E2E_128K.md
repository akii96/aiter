# TP2 MXFP4 MoE at `inter_dim=1536` — end-to-end validation at 128k ISL

End-to-end serving measurement of the tuned rows + gate entry on MiniMax-M3-MXFP4 at TP=2.
Supersedes the op-level-only evidence in `FINDINGS.md` with a served result.

**Headline: a prefill-proportional win.** It pays in proportion to how much of the MoE work
is long-context prefill. At 8k ISL the same patch is indistinguishable from zero; at 128k it
is a clear, reproducible gain.

---

## 1. Result

MiniMax-M3-MXFP4, TP=2, 8×MI355X node (2 devices used), ROCm 7.2.3,
vLLM `0.30.1rc1.dev143+g29468dde8`, aiter wheel `0.1.22.post1` (**unmodified**).
128k ISL / 1k OSL, `--max-num-batched-tokens 32768`.
One cold repeat discarded, 3 measured, GPU asserted idle between repeats.

| conc | stock | patched | delta | resolution limit | verdict |
|---:|---:|---:|---:|---:|---|
| 4 | 20704.4 tok/s (sd 0.41%) | **20929.1** (sd **0.04%**) | **+1.09% ± 0.29%** | 0.58% | outside noise |
| 8 | 23922.2 tok/s (sd 0.30%) | **24115.5** (sd 0.21%) | **+0.81% ± 0.26%** | 0.52% | outside noise |

At conc 4 **every patched repeat exceeds every stock repeat**; the distributions do not
overlap. TTFT moves 10891 → 10739 ms (−1.4%) at conc 4 and 19133 → 18904 ms (−1.2%) at
conc 8 — an internal consistency check, since a prefill-side kernel win should appear in
time-to-first-token.

Per-repeat, total token throughput (tok/s):

```
conc 4  stock   20660.4  20615.0  20818.6  20679.5
        patched 20869.6  20917.4  20934.0  20936.1
conc 8  stock   24040.4  24009.2  23924.9  23832.4
        patched 24157.4  24149.4  24153.5  24043.5
```

### Resolution limit

Both arms sit at sd ≈ 0.2–0.4% with n=3 warm repeats, so the standard error on the mean is
≈ 0.2% and a two-arm difference is only distinguishable above ≈ 0.5-0.6% (propagating both arms' SEM through the ratio). Both deltas clear
that; a smaller delta would have to be reported as *below resolution*, not as a win.

## 2. Why 128k wins where 8k did not

The same patch, measured on two workloads:

```
8k ISL:    +0.02% ± 0.30%    tuned bucket hit ~4 of ~44 MoE calls
128k ISL:  +1.09% ± 0.29%    bucket 32768 = 100% of prefill MoE work
```

Same kernel, same node, same code. The only variable is **what fraction of MoE work lands on
the tuned path**. This was *predicted by the bucket probe before the sweep was run*, not
inferred afterwards.

**Scope, stated plainly:** decode is structurally outside the gate. Buckets 1–128 resolve
activations to bf16 (`GPTOSS_SWIGLU_MXFP4_BF16_BOUND=256`, SEPARATED gate mode) and take the
a16w4 family, which `_is_mxfp4_kname` (`startswith("flydsl_mxmoe_g")`) does not match. A
decode-dominated workload sees nothing from this patch.

**Kernel-to-e2e ratio:** the MoE op itself is 10–21% faster in isolation; e2e is ~1%. MoE
GEMM is a minority of the trace even at 128k, and the rows cover prefill only. That ratio is
the useful number for predicting what this does on another workload.

## 3. Engagement, verified two-sided from the live servers

```
arm0 stock  : mxmoe=0  "2stage default"=48  discard=0  preempt=0
arm1 patched: mxmoe=4  "2stage default"=40  discard=0  preempt=0
both        : enable_prefix_caching=False, max_num_batched_tokens=32768 (resolved config)
```

Stock shows **zero** `flydsl_mxmoe_g1_a4w4` and falls back to the heuristic; patched dispatches
`flydsl_mxmoe_g1_a4w4_128x256x256_swiglu_xcd4` + `flydsl_moe2_layout_afp4_wfp4_bf16_t128x128x128_atomic_sbm128`.

Note stock produces **no** "discarding MXMOE config" warning — it has no `inter_dim=1536`
rows at all, so `cfg is None` and that branch is unreachable. An engagement check that expects
the warning on a stock baseline is testing for something that cannot happen.

## 4. Bucket coverage

`get_padded_M` is **nextPow2 below 32768** (`_PADDED_M_TIERS` applies only at/above 32768), so
`8193 → 16384`. With chunked prefill the bucket follows the *actual packed step size*, not the
budget: `--max-num-batched-tokens` is a ceiling, and a 131072-token prompt divides exactly into
both 16384 (×8) and 32768 (×4), so every prefill chunk is full-size.

| budget | prefill bucket | tuned |
|---|---|---|
| 16384 | 16384 | ✅ |
| 32768 | 32768 | ✅ |

**Limitation:** only the *exact* buckets are tuned. A ragged tail chunk falls back silently —
at ISL 100k with budget 32768 the 1,696-token tail resolves to bucket 2048 and takes
`2stage default` (~1.7% of prefill tokens). The patch covers 100% of prefill MoE work only
when ISL is an exact multiple of the batch-token budget.

## 5. Required environment — three flags, all defaulting to False

- `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` — **load-bearing.** The tuned rows key on
  `(129, 6144, 1536, 5)`: 128 routed + 1 shared expert, topk 4+1. Without fusion the runtime
  asks `(128, 4)`, the lookup misses, and the patch does **nothing, with no warning and no
  error**. Derived from the model config: `num_local_experts=128`, `num_experts_per_tok=4`,
  `n_shared_experts=1`, `intermediate_size=3072` (→ 1536 at TP2).
- `VLLM_ROCM_USE_AITER=1` **and** `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1` — without **both**,
  `--attention-config '{"indexer_kv_dtype":"fp8"}'` is a hard crash in worker init
  (`NotImplementedError: indexer_kv_dtype='fp8' is not supported by the Triton indexer impl`).

Either add rows keyed for the unfused `(128, 4)` shape, or document the fusion flag as a hard
requirement for these rows to take effect.

## 6. Accuracy

n=5 prompts, temperature 0, fixed seed. **This is a smoke test, not a scored evaluation.**

### ⚠️ Token-exact diffing is an INVALID test on this stack

The stock server **diverges from itself** on identical temperature-0 calls — including the
long-context case. Repeating a prompt against the *same unmodified server* does not reproduce
its own output. Any "N/5 exact match" figure between two arms is therefore meaningless here:
it measures run-to-run nondeterminism, not the patch.

Likely sources: atomic-epilogue reduction order in the MoE (a same-config noise floor of
~3.6e-3 relative was measured directly on this op), and non-deterministic all-reduce ordering
at TP=2. **Verify self-consistency before trusting any exact-match accuracy comparison.**

### What was actually tested

Semantic equivalence on checkable content:

```
long_needle  BOTH recover '8317-QUARTZ-99'   <- 128k retrieval, bucket 32768: 5/5 vs 5/5
reasoning    both reach 395 with the same working (17*23=391, 144/12=12, 403-8=395)
code         both emit a correct fibonacci
prose        both on-task
short_fact   both answer Paris and Berlin correctly, then both drift
```

**No degradation.** The long-context retrieval — the only case that engages the patched
kernel — succeeds 5/5 on both arms.

`short_fact` drifting on both arms is a **harness artefact, not a kernel or model issue**: the
prompt is plain text (`Q: What is the capital of France? A:`, 11 tokens) sent to
`/v1/completions`, so a chat-tuned model receives no chat template and, given 192 tokens to
fill, continues past the answer and invents its own scaffolding. An 11-token prompt is a bf16
decode bucket, which the patched kernel structurally cannot reach.

Absence of degradation is **not proven** at n=5; a real claim needs lm-eval or a long-context
retrieval suite.

## 7. Methodology notes worth reusing

**`lru_cache` makes log-diffing report the opposite of the truth.** `get_2stage_cfgs` is
`@functools.lru_cache(maxsize=2048)`, so each distinct key logs its dispatch line exactly once
per worker — during startup warmup. Diffing the log across a request shows **zero** new lines.
*"No new dispatch lines" is indistinguishable from "no dispatch".*

The clean way to prove live dispatch: send a prompt whose chunking must produce a
**never-before-seen bucket**, and predict it in advance. A 100k prompt at budget 32768 is
3 full chunks + a 1,696-token tail → `get_padded_M(1696)=2048`. Exactly one new bucket
appeared, `2048`, and nothing else.

**A long-ISL bench can outlive its client.** A harness timeout killed the controlling process
while `vllm bench serve` kept running inside the container; the next repeat then drove the same
server concurrently — `Running: 16` during a `--max-concurrency 8` bench — producing −27%
throughput and +77% TTFT that mimics preemption or thermal throttling. It is neither.
Diagnostic: sample `rocm-smi` *before* each repeat; a clean repeat reads 0–1%, a contaminated
one reads 100% before sending a single request. Fix: assert GPU-idle and no live bench between
repeats. KV was never the constraint — capacity 4,268,544 tokens, 32.07× headroom at 133,120
tok/request, `grep -ci preempt` = 0 across the entire sweep.

## 8. Reproduce

```bash
# tune (pre-warm the JIT cache first; ~9 min for both buckets on 2 GPUs)
python3 csrc/ck_gemm_moe_2stages_codegen/gemm_moe_tune.py --mxfp4-flydsl \
  -i untuned.csv -o tuned.csv --errRatio 0.05 --mp 2 --shape_grouped
# errRatio 0.01 rejects 100% of candidates: it sits below the MXFP4 quantisation
# floor (~0.01175), so it is a step function, not a discrimination curve.

# serve (both arms identical except the image)
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 \
VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1 VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1 \
vllm serve amd/MiniMax-M3-MXFP4 --tensor-parallel-size 2 --kv-cache-dtype fp8 \
  --block-size 128 --no-enable-prefix-caching --language-model-only \
  --max-model-len 133120 --gpu-memory-utilization 0.95 \
  --max-num-batched-tokens 32768 --max-num-seqs 128 --enable-chunked-prefill \
  --async-scheduling --moe-backend aiter \
  --attention-config '{"backend":"ROCM_AITER_UNIFIED_ATTN","indexer_kv_dtype":"fp8"}'

# bench
vllm bench serve --backend openai --model amd/MiniMax-M3-MXFP4 --dataset-name random \
  --random-input-len 131072 --random-output-len 1024 --max-concurrency 4 --num-prompts 8 \
  --ignore-eos --seed 5
```
